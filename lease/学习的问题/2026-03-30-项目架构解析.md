# 尚庭公寓：Spring Boot 项目架构与数据流转解析（通俗易懂版）

如果我们把开发一个后端系统比作**开一家大型的高级餐厅**，那么 Spring Boot 就是这座餐厅的地基和精装修，而你写的各类代码就是餐厅里各个岗位分工明确的员工。

下面我们跟着一次“顾客点餐（前端请求）”的全过程，来看看各个层和几大核心技术是怎么配合工作的。

---

## 一、 核心架构分层（餐厅的组织架构）

在项目中，你会经常看到以不同名称结尾包名或类名，它们各司其职：

### 1. Controller 层（前台接待员 / 服务员）
- **作用**：负责直接面对前端（顾客）。它接收前端发来的 HTTP 请求（点菜），检查一下请求参数（看看菜单上有没有这道菜），然后把任务交给后厨（Service层），最后把做好的菜（数据）端给前端。
- **特点**：代码很薄，主要负责“调度”，绝不在这写复杂的业务逻辑。

**【代码大揭秘】**：
```java
@RestController
@RequestMapping("/app/notification")
public class NotificationController {
    @Autowired
    private NotificationService notificationService; // 呼叫主厨

    @GetMapping("/list")
    public Result<List<NotificationVO>> list() {
        Long userId = LoginUserHolder.getUserId(); // 识别是哪位顾客(获取张三ID)
        List<NotificationVO> list = notificationService.getNotificationList(userId); // 交代主厨做菜
        return Result.ok(list); // 将装好盘的菜(VO)放进标准托盘(Result)，端给前端
    }
}
```

### 2. Service 层（餐厅主厨）
- **作用**：负责核心的**业务逻辑**（炒菜）。如果有退单、加急、满减优惠等复杂规则，全在这里处理。它不仅能自己切菜，还能指挥仓库管理员去找食材。
- **特点**：项目中最复杂、最厚的一部分。

**【代码大揭秘】**：
```java
@Service
public class NotificationServiceImpl extends ServiceImpl<NotificationMapper, Notification> implements NotificationService {
    
    @Override
    public List<NotificationVO> getNotificationList(Long userId) {
        // 1. 主厨找仓库管理员要食材（向数据库发指令查询数据）
        LambdaQueryWrapper<Notification> query = new LambdaQueryWrapper<>();
        query.eq(Notification::getUserId, userId);
        List<Notification> entities = this.baseMapper.selectList(query);
        
        // 2. 将毛坯食材(Entity)洗好切好，精美摆盘(转换为前端需要的VO)
        List<NotificationVO> voList = new ArrayList<>();
        for (Notification entity : entities) {
            NotificationVO vo = new NotificationVO();
            BeanUtils.copyProperties(entity, vo); // 数据属性拷贝
            voList.add(vo);
        }
        return voList;
    }
}
```

### 3. Mapper 层（仓库管理员）
- **作用**：专门负责和数据库（大仓库）打交道。主厨需要什么清单（查询），或者进了一批新货（插入、更新），仓库管理员负责准确无误地从 MySQL 数据库搬运数据。

**【代码大揭秘】**：
```java
@Mapper
public interface NotificationMapper extends BaseMapper<Notification> {
    // 因为继承了 MyBatis-Plus 的 BaseMapper，
    // 这里其实已经自带了 insert、deleteById、selectList 等几十种基础拉货技能。
    // 除非遇到极其复杂的跨表联合查询，才需要在这里手写专门的 SQL，否则这里可以一行代码不写。
}
```

### 4. 数据载体对象（各种盛装食物的盘子）
数据在不同层之间流转时，要装在不同的对象里：
- **Entity（实体类）**：原生态食材。从数据库拔出来长啥样，Entity 就长啥样（和数据库表字段一一对应）。
- **VO (View Object，视图对象)**：精美的摆盘。专门为了让前端页面展示而设计的对象。比如数据库里存的是“男/女”的数字 1 或 0，VO 里可能就直接转成前台展示要用的多语言字符串了，而且还会剔除掉前端不需要的敏感字段（如密码）。
- **DTO (Data Transfer Object)**：顾客的点单条。前端传给后端的复杂请求参数集合。

### 5. Custom / Commons / Config 层（餐厅的规章制度与基础设施）
- **作用**：存放一些跨越各个层级都得用的功能。比如连接池配置、统一的异常捕获（有人闹事怎么处理）、JWT 登录拦截器（保安查验VIP身份）等。

## 二、 数据的流动（一道菜是如何上桌的？）

假设前端用户在移动端 APP 点击了【查看我的通知消息】按钮：

1. **[APP/浏览器]** 发出请求：`GET /app/notification/list`
2. **[Controller]** 层收到请求，发现是张三（解析Token），于是它冲着后厨喊：`service.getNotificationList(张三的ID)`
3. **[Service]** 层拿到张三的ID，开始做菜。主厨发现自己手里没食材，于是转身找仓库管理员：`mapper.selectByUserId(张三的ID)`
4. **[Mapper]** 收到指令，生成了一段 SQL 语句去查询 MySQL 数据库。
5. **[数据库 MySQL]** 返回了原始的数据行。
6. **[Mapper]** 把这些原始数据行打包成 **Entity 对象** 交给主厨。
7. **[Service]** 主厨发现原始数据太粗糙（比如时间格式不对，或者要把外键 ID 变成具体的名字），经过一番加工，把 Entity 对象换成好看的 **VO 对象**（装盘）。
8. **[Controller]** 服务员接过 VO 对象，用一个统一的 `Result` 对象（标准托盘，里头带上状态码比如 code: 200，操作成功）端回到前端。
9. **[APP/浏览器]** 提取里面的数据，渲染出漂亮的用户界面！

## 三、 核心技术在这个流程里扮演什么角色？

为了让这套流程走得快、走得稳、好看，我们引入了几个外部“黑科技设备”：

### 1. Knife4j —— 餐厅的“电子全息菜单”
- **它是做什么的**：它是基于 Swagger 的一个增强版接口文档工具。
- **在项目中的作用**：如果你不写菜单，前端开发人员怎么知道你能提供什么接口？Knife4j 可以自动扫描你的 Controller，把每个接口（菜名）、请求参数（口味要求）、返回值（菜品实物）生成非常漂亮的网页版文档。
- **举例**：你不仅能在网页上查文档，还能直接在上面填参数并发起请求来**试吃**（测试接口），免去了手写 Postman 的繁琐。

**【代码大揭秘】**：
```java
@Tag(name = "通知管理模块") // 生成该菜单的大类标题
@RestController
public class NotificationController {

    @Operation(summary = "获取未读消息数量", description = "给前端展示小红点用的") // 生成具体的接口菜名和介绍
    @GetMapping("/unreadCount")
    public Result<Integer> getUnreadCount() { ... }
}
```

### 2. MyBatis-Plus & MyBatisX —— 高智能“自动取货机器人”
- **它是做什么的**：它是我们的持久层框架（升级版的 Mapper 帮手）。
- **在项目中的作用**：以前仓库管理员要去库房拿东西，要自己手写长长的 SQL 纸条。有了 MyBatis-Plus，像“增删改查”这种最基础的进出库动作，自带机器人帮你完成，你根本不需要写一条 SQL 语句（只要调用 `mapper.insert()`, `mapper.selectById()` 即可）。MyBatisX 则是 IDEA 里的插件，能帮你一键生成 Entity、Mapper 和 Service 的基础代码骨架。

### 3. Redis —— 餐厅前台的“保温取餐柜 / 快速记忆屏”
- **它是做什么的**：一个极其快速的内存级别的数据库。
- **在项目中的作用**：MySQL 的硬伤是每次都要去硬盘读取，比较慢。对于一些**频繁读取又不太常变化**的数据（比如手机验证码、JWT 登录令牌 accessToken、房间所在城市的字典列表），我们可以放在 Redis 里。
- **举例数据流动**：用户再次请求登录验证码，Service 不去 MySQL 查了，直接从 Redis 取出之前存的验证码进行比对。速度快了上百倍！如果 5 分钟没用，Redis 还会自动让验证码过期销毁（TTL机制）。

**【代码大揭秘】**：
```java
@Autowired
private StringRedisTemplate redisTemplate;

public void sendVerifyCode(String phone) {
    String code = "123456"; // 假设施设生成的验证码
    String key = "app:login:phone:" + phone;
    
    // 把验证码放进 Redis (相当于放在保温取餐柜)，并设定 5 分钟后自动过期销毁
    redisTemplate.opsForValue().set(key, code, 5, TimeUnit.MINUTES);
}

public void login(String phone, String codeInput) {
    // 从 Redis 极速提取验证码比对，不用慢吞吞去查 MySQL
    String realCode = redisTemplate.opsForValue().get("app:login:phone:" + phone);
    if (!codeInput.equals(realCode)) {
        throw new LeaseException("验证码错误或已过期！");
    }
}
```

### 4. MinIO —— 独立的“超大冰柜 / 专用图床云仓库”
- **它是做什么的**：企业级的对象存储服务（用来专门存文件、图片、视频的对象）。
- **在项目中的作用**：在业务系统的数据库（MySQL）中，存大图片是非常愚蠢且低效的。MySQL 就像精密的抽屉，只适合存文字数据。
- **举例数据流动**：用户上传一张公寓的卧室实拍图。
    1. Controller 接收到图片文件。
    2. Service 直接把文件塞进 **MinIO** 这个专用的超大冰柜里。
    3. MinIO 存好后，返回一个下载链接（比如 `http://你的IP:9000/lease/abcd.jpg`）。
    4. Service 把这个纯文本形式的 **URL 链接** 交给 Mapper。
    5. Mapper 把这个短小精悍的 URL 字符串存进 MySQL 的 `url` 字段中。
    6. 前端读取时，拿到的是字符串，前端直接用 `<img src="这个URL">` 去 MinIO 拉取图片，避免给我们的 Spring Boot 核心服务造成带宽负担。

**【代码大揭秘】**：
```java
@Autowired
private MinioClient minioClient;

public String uploadImage(MultipartFile file) throws Exception {
    String filename = UUID.randomUUID() + "-" + file.getOriginalFilename();
    
    // 把几十兆的高清图片输入流直接塞进 MinIO 大冰柜
    minioClient.putObject(PutObjectArgs.builder()
        .bucket("lease")
        .object(filename)
        .stream(file.getInputStream(), file.getSize(), -1)
        .contentType(file.getContentType())
        .build());
    
    // MinIO 存储完毕后，拼装成一个短小且直接可访问的 URL 给我们
    // 我们最终只把这行字符串存进 MySQL 数据库
    return "http://我们云主机的IP:9000/lease/" + filename;
}
```
